# 从 Python 工程到量化回测：Quant Lab 项目教程

这份教程面向熟悉 Python、算法和工程实践，但刚接触交易研究的读者。你不需要补学 Python；需要建立的是交易账户、信息时间和实验可信度的概念。

读完后，你应该能回答：一笔交易为什么发生、什么时候发生、成交多少股、现金为什么变化、结果有没有偷看未来，以及报告中的收益究竟代表什么。

本文对应仓库当前实现，历史结果取自 `reports/metrics.json`。人工案例是教学数据，成本参数会明确标出；它们不是默认历史回测参数。

## 1. 项目到底在做什么

量化交易的基本做法，是把交易判断写成明确规则，再用数据检验这些规则。
规则可以非常简单，也可以非常复杂。这个项目选择一个简单规则，方便检验基础工程。

当前程序进行的是历史回测：把过去的行情按时间顺序交给一个模拟账户，记录如果按指定规则交易，账户会如何变化。
它不连接交易账户，不向市场发送真实订单。

用算法工程的语言，可以把它看作带信息约束的离散状态机：

```text
输入：历史行情、策略配置、成本配置、初始现金
状态：现金、持仓股数、成本基础、累计已实现损益
事件：交易日开盘、交易日收盘
输出：成交记录、逐日账户状态、绩效统计、审计信息
```

和普通离线数据处理相比，区别在于：程序拿到完整历史数据，并不意味着每个时刻都允许使用所有数据。
模拟中的每个交易判断，都必须遵守当时的信息边界。

对于一个算法模型，“拿未来标签当输入”会造成数据泄露；对于回测，“提前知道明天的收盘价”会让交易结果失真。
但回测还多了一层：即使预测信号没有泄露，如果成交时点或账户核算错误，最终收益仍然可能是假的。

本项目验证的是这条完整链路：

```mermaid
flowchart LR
    A[冻结的日线行情] --> B[历史收盘均线]
    B --> C[收盘目标仓位]
    C --> D[次日开盘成交]
    D --> E[更新现金和持仓]
    E --> F[收盘估值]
    F --> G[绩效与审计报告]
```

## 2. 先认识交易里的对象

### 2.1 SPY、ETF 和交易标的

`symbol` 是交易标识符，本项目使用 `SPY`。
SPY 是一只 ETF，目标是在费用扣除前大体跟踪标普 500 指数的价格与收益表现。[发行方介绍](https://www.ssga.com/us/en/individual/etfs/state-street-spdr-sp-500-etf-trust-spy)

ETF 可以在交易所买卖，一份 ETF 代表对其投资组合的一部分权益。[Investor.gov 的 ETF 说明](https://www.investor.gov/introduction-investing/investing-basics/glossary/exchange-traded-fund-etf)

本项目无需逐个处理指数成分股。程序把 SPY 当作一个有价格、成交量、可按份数买卖的标的。
代码里的 `quantity` 就是持有的份数，后文为了方便称为“股数”。

### 2.2 买入、卖出、持仓和现金

假设你有 10,000 美元，花 9,000 美元买入 90 股，每股价格 100 美元。
忽略交易成本，此时：

```text
cash = 1,000              # 没有用于买股票的资金
quantity = 90            # 账户拥有的股票数量
market_value = 9,000     # 持仓按当前价格的价值
equity = 10,000          # 现金加持仓价值
```

如果价格涨到 110 美元，但没有卖出：

```text
cash = 1,000
quantity = 90
market_value = 9,900
equity = 10,900
```

现金没有变化，账户资产增加了 900 美元。这就是尚未兑现的持仓盈利。

因此，观察 `cash` 不能判断账户是否赚钱。买入后现金通常大幅下降，但这笔钱转换成了股票。
要观察的是 `equity`，即总资产净值。

### 2.3 long / cash 是两个账户状态

本项目只有两种方向：

| 术语 | 含义 | 代码体现 |
| --- | --- | --- |
| long，持有多头 | 拥有 SPY，价格上涨通常有利于账户 | `quantity > 0` |
| cash，空仓 | 不持有 SPY，仅持现金 | `quantity == 0` |

“空仓”不是“做空”。空仓是不持有；做空涉及借入并卖出标的，本项目没有实现。

买入使用可用现金尽量购买整数股，不借钱。因为不能买零碎股，仍可能留下少量现金。
持仓期间不会每天把零头现金再投入，也不会每天重新配置仓位。

### 2.4 信号、订单、成交是不同事件

| 对象 | 回答的问题 | 本项目对应 |
| --- | --- | --- |
| 指标 indicator | 历史数据有什么统计特征？ | `fast_ma`、`slow_ma` |
| 目标 target | 规则希望处于什么状态？ | `-1`、`0`、`1` |
| 信号 signal | 当前账户需要做什么？ | BUY、SELL、HOLD、WAIT |
| 订单意图 | 这次尝试买还是卖？ | 回测里的 `side` |
| 成交 fill | 实际成交了多少，付出什么成本？ | `Fill` |
| 账户状态 | 成交后还剩多少钱、多少股？ | `Portfolio` |

这个工程没有独立的订单队列类。回测循环决定买卖方向，`execute_order` 返回成交结果。
如果买不起一股，就返回 `None`，没有成交记录。

## 3. 看懂一行日线行情

数据表每行代表一个交易日，包含 OHLCV：

| 字段 | 含义 | 当日什么时候能够完整确定 |
| --- | --- | --- |
| `date` | 纽约交易所会话日期 | 日期标签本身可预先知道 |
| `open` | 该日开盘价格 | 开盘之后 |
| `high` | 当日最高价格 | 整个交易日结束之后 |
| `low` | 当日最低价格 | 整个交易日结束之后 |
| `close` | 当日收盘价格 | 收盘之后 |
| `volume` | 当日总成交量 | 整个交易日结束之后 |

教学用的一行数据：

```text
date        open   high   low   close   volume
2020-01-02  100    105     98    103     1000
```

它不告诉你盘中的完整价格路径。
你不知道当天先到 105 还是先到 98，也不知道每个价位有哪些订单。
所以不能仅凭日线可靠推断复杂盘中条件单的执行顺序。
当前实现只做开盘成交和收盘估值，避免引入这些无法从日线确定的问题。

### 3.1 交易日不等于日历日

20 日均线在本项目指最近 20 行交易日收盘数据，不是最近 20 个自然日。
周末和休市日没有交易行。

代码中的 `T+1` 表示下一交易日。通常，周五收盘信号要在下一个交易日开盘执行，而不是周六。
当前实现把冻结数据的下一行视为下一交易日，所以缺失交易行可能改变模拟执行时间。

### 3.2 复权价格：为什么历史价格不一定是真实成交报价

公司分红或拆股会改变价格序列的解释方式。
例如，简化地考虑一只股票从 100 美元价格中支付 2 美元现金分红，除息价格可能相应降低。
如果只看价格变化，可能误以为持有人无缘无故损失了这 2 美元，而忽略收到的分红。

复权数据对历史价格作调整，帮助把公司行动的影响纳入可比较的价格序列。
下载脚本使用 `auto_adjust=True`，并且 OHLC 都采用同一复权口径。

这有两个后果：

1. 回测没有另外把分红现金加入账户，避免在当前合成价格模型中重复计入。
2. 复权后的历史价格及其整数股数，并不严格等于当时真实美元价格和真实股数。

因此，当前 `Portfolio` 是基于复权价格的合成账户。
它适合验证基础计算链路，但不能直接解释成可逐笔重演的真实历史现金交易。

另一个细节：`raw_open` 中的 raw 意味着“没有施加模拟滑点”，并不意味着“未复权”。
当前日志的 `raw_open` 仍来自复权日线。

## 4. 20/60 均线策略怎么理解

策略代码见 [`src/strategy.py`](../src/strategy.py)。

简单移动平均线 SMA 是过去若干个收盘价的算术平均：

```text
fast_ma[t] = mean(close[t-19], ..., close[t])
slow_ma[t] = mean(close[t-59], ..., close[t])
```

20 日均线反映较短时间的平均价格；60 日均线反映较长时间的平均价格。
短均线高于长均线，可以理解为近期价格均值高于较长历史均值。
策略将这种状态解释为应该持有 SPY；否则持现金。
这种解释是一条研究假设，不是“明天一定上涨”的结论。

代码非常直接：

```python
result['fast_ma'] = close.rolling(fast_window, min_periods=fast_window).mean()
result['slow_ma'] = close.rolling(slow_window, min_periods=slow_window).mean()
result['target'] = (result.fast_ma > result.slow_ma).astype(int)
result.loc[result.slow_ma.isna(), 'target'] = -1
```

`rolling(20)` 包含当前行及其之前的 19 行，不读取后面的行。
`min_periods=20` 要求窗口完整，不用不足 20 行的均值代替正式指标。

`target` 的定义是：

| 数值 | 含义 |
| --- | --- |
| `-1` | 长均线尚未准备好，不能进行正式决策 |
| `0` | 希望持现金 |
| `1` | 希望持有 SPY |

两条均线相等时，条件 `fast_ma > slow_ma` 为假，目标为现金。

### 4.1 这是状态规则，并非只检测交叉瞬间

代码没有要求“今天发生了金叉”才买入。
它检查的是：前一个收盘目标为持有，而当前账户没有持仓，就尝试买入。

假设预热结束当天短均线已经高于长均线，就可以在下一交易日首次买入。
无需再等待一个新的上穿事件。
如果买入成功，后续目标继续为 1 时会保持持仓，不重复买入。

### 4.2 预热期为什么是 60 个交易日

前 59 行没有完整的 60 日均线，目标为 `-1`。
第 60 个交易日收盘，首次有足够数据计算完整长均线。
这个目标只能在第 61 个交易日开盘用于成交。

注意 Python 下标：

```text
第 60 个交易日 -> iloc[59]
第 61 个交易日 -> iloc[60]
```

这是测试中经常出现 59 和 60 的原因。

## 5. 最重要的时间线：什么时候知道，什么时候执行

当前规则：

```text
T 日收盘结束
    得到 close[T]
    计算均线和 target[T]
    根据当前持仓知道是否需要买卖

下一交易日开盘
    用 target[T] 决定方向
    用 open[T+1] 模拟成交价
    扣除成本并更新账户

下一交易日收盘
    用 close[T+1] 对持仓估值
    得到新的 target[T+1]
```

核心代码在 [`src/execution.py`](../src/execution.py)：

```python
return -1 if row_number == 0 else int(targets[row_number - 1])
```

模拟第 `i` 行开盘时，使用的是 `targets[i-1]`，不是 `targets[i]`。
当前行的 close、high、low、总成交量都不能用于当日开盘买卖判断。

错误做法是先用今天的最终收盘价判断方向，再假设在今天的收盘价成交。
在该价格已经确定后，不能倒回那个时刻完成交易。

### 5.1 为什么可以一次性计算整张指标表

`run_backtest` 先对完整数据执行 `calculate_signals`，然后逐日模拟。
看到“完整数据”不必立即认定为泄露。要检查函数的数据依赖。

当前每行指标只依赖该行和之前的 close：

```text
indicators[i] = f(close[0:i+1])
```

这是因果计算。只要模拟开盘时读取前一行指标，它与逐日只传入历史前缀计算，在逻辑上是一致的。
一次性计算只是方便使用 pandas，不改变可用信息边界。

如果以后把全样本归一化、居中滚动或全样本拟合加入策略，这个结论就不再自动成立。
必须重新检查依赖，并运行未来变异测试。

```text
quant-lab/
├── config/                  策略参数、账户和成本配置
├── data/raw/                冻结行情和下载元数据，Git 忽略
├── docs/                    方案、策略规范和本教程
├── reports/                 输出结果，Git 忽略
├── scripts/
│   ├── download_data.py     显式联网下载
│   └── run_backtest.py      从本地数据运行完整流程
├── src/
│   ├── data_loader.py       本地读取与哈希
│   ├── strategy.py          指标与目标
│   ├── execution.py         成交与费用
│   ├── portfolio.py         账户核算
│   ├── backtest.py          按时间推进
│   ├── metrics.py           完成后计算统计量
│   └── validation.py        数据和因果性检查
└── tests/                   人工可验证的确定性测试
```

这不是为了增加抽象层，而是让错误有清晰的归属。
例如，策略算出正确的目标，但现金扣错，应该检查 `execution.py` 和 `portfolio.py`。
如果当天就执行了当天收盘信号，应该检查 `backtest.py` 的时间推进。

`strategy.py` 没有现金参数，不知道持仓多少，也不决定买多少股。
这是设计上的边界：市场状态判断与账户约束各自独立。

`Portfolio` 使用类，是因为现金、股数、成本基础需要一起维护。
`Costs`、`Fill`、`BacktestResult` 是 dataclass，用来表达清晰的数据结构，没有复杂继承层次。

## 7. 数据读取和验证为什么是独立步骤

下载与回测分开，有利于复现同一个实验。
如果每次回测都重新下载，供应商修订数据后，即使代码不变，结果也可能变化。

[`scripts/download_data.py`](../scripts/download_data.py) 负责联网、复权设置、列名标准化、日期转换和保存。
下载区间的业务结束日期是包含边界的 `2025-12-31`；yfinance 的接口结束日期是排他边界，所以脚本传入下一天。[yfinance 接口说明](https://ranaroussi.github.io/yfinance/reference/yfinance.price_history.html)

冻结输出有两个文件：

```text
data/raw/spy_daily.parquet
data/raw/spy_daily.metadata.json
```

元数据保存来源、下载时间、复权设置、真实日期范围、行数和 SHA-256。
脚本拒绝覆盖已有数据。已经下载后，日常运行只执行回测脚本。

[`src/data_loader.py`](../src/data_loader.py) 的 `load_market_data` 只读本地 Parquet，不联网。
它先验证完整文件，再选择实验日期区间，最后重置行索引。
回测入口检查文件哈希及元数据，且运行后再次检查数据文件没有变化。

### 7.1 为什么不自动排序、去重、填空

某些数据分析脚本会写：

```python
data.sort_values('date').drop_duplicates('date').ffill()
```

在研究基础工程中，这些操作可能掩盖数据问题。
重复日期保留哪一行？缺失 close 用昨天价格是否合理？缺失的 open 可以用昨日 close 代替吗？
这些都是会影响交易结果的决策，不能静默完成。

当前验证遇到以下情况直接失败：日期重复、逆序、缺失值、非正价格、无限值、不合法 OHLC、负成交量、时区或时间部分不符合约定等。
数据清洗如果以后需要加入，应该作为独立、可记录的步骤，而非在回测中临时改变历史。

### 7.2 日期标签与时区

当前 date 是纽约交易所的当地会话日期，不是精确成交时间戳。
下载先转到 `America/New_York`，再去掉时区并归一到日期。
因此你在中国运行程序，也不应该把这些标签再自动转换成中国日期。

时区去掉不表示原数据来自 UTC。它表示项目约定：这一列只存交易所当地日期。

## 8. execution.py：方向确定后，如何模拟成交

成交函数接受：

```python
execute_order(side, raw_open, cash, position, costs)
```

这是一个不修改账户的计算函数。输入现金和仓位，它计算是否能成交、成交多少、花费多少；返回一个不可变 `Fill`。
真正改账户的是下一节的 `Portfolio.apply_fill`。

### 8.1 滑点：成交价格比参考价格差一点

模拟成交不会直接使用开盘价格，而是假设付出一定不利价格偏移：

```python
buy_price = raw_open * (1 + slippage_rate)
sell_price = raw_open * (1 - slippage_rate)
```

买入价格更高，卖出价格更低，均降低账户表现。
默认滑点为 `0.0002`，也就是 0.02%，不是 2%。

这是一种简化成本假设，并非程序推导出真实市场一定有这么多滑点。
真实成交可能受买卖价差、流动性、订单规模和到达时机等因素影响。

### 8.2 手续费：根据成交金额额外支付

```python
trade_value = quantity * execution_price
commission = trade_value * commission_rate
```

默认手续费为 `0.0005`，即 0.05%。买入和卖出都会收取。

例如，成交金额 10,000 美元时，手续费为 5 美元。
不能把“股票涨了 1%”直接视为“账户赚了 1%”，因为还有费用、持仓时间和闲置现金。

### 8.3 买入数量必须考虑手续费

```python
quantity = floor(cash / (execution_price * (1 + commission_rate)))
```

分母是一股股票的成交价加上对应手续费。
只使用 `floor(cash / raw_open)`，会忽略滑点和手续费，有可能买得太多。

代码还有一个递减检查，防止浮点数在整数边界附近把数量多算一股。
这是账户正确性保护，不是收益优化。

### 8.4 五个成本字段不要混淆

| 字段 | 定义 | 用途 |
| --- | --- | --- |
| `raw_open` | 数据中的开盘价，未施加模拟滑点 | 参考基准 |
| `execution_price` | 施加滑点后的成交价 | 计算实际成交金额 |
| `trade_value` | 股数 × 成交价 | 现金结算基础 |
| `commission` | 成交金额 × 手续费率 | 额外现金费用 |
| `slippage_cost` | 股数 × 成交价和参考价之差的绝对值 | 成本归因 |

现金买入扣款是 `trade_value + commission`。
不能再加 `slippage_cost`，因为滑点已经通过 `execution_price` 进入 `trade_value`。
否则会重复收费。

滑点成本总和也不一定等于“有滑点回测与无滑点回测期末资产的差值”。
改变成本可能改变整数股数、剩余现金以及后续复利路径；日志中的成本是对已经发生的这些成交逐笔归因。

## 9. portfolio.py：如何正确记账

[`src/portfolio.py`](../src/portfolio.py) 维护四个状态量：

```python
cash          # 可用现金
quantity      # 持仓股数
cost_basis    # 当前持仓总成本，含买入手续费
realized_pnl  # 历史已完成卖出累计损益
```

`PnL` 是 profit and loss，表示盈亏。

### 9.1 买入

```python
debit = fill.trade_value + fill.commission
cash -= debit
quantity = fill.quantity
cost_basis = debit
```

买入产生持仓，成本基础记录你为这笔持仓实际支付的总金额。
买入手续费不需要等到卖出才“发生”，买入后立刻影响净值。

### 9.2 卖出

```python
proceeds = fill.trade_value - fill.commission
cash += proceeds
realized_pnl += proceeds - cost_basis
quantity = 0
cost_basis = 0
```

卖出收到的是扣除卖出手续费后的净收入。
净收入减去含买入费用的成本，得到完整往返净盈亏。

当前每次卖出全部持仓，不处理部分卖出，因此不需要选择 FIFO、平均成本等复杂成本分摊规则。

### 9.3 未实现损益与总资产

```python
market_value = quantity * close
equity = cash + market_value
unrealized_pnl = market_value - cost_basis
```

未实现损益是以当前估值计算的持仓盈亏，尚未卖出。
它包含已经支付的买入费用，但不扣除尚未发生的未来卖出费用。
当前期末不强制卖出，因此期末总资产也没有扣除假设清仓成本。

在没有外部入金、出金、单独分红现金或利息的当前模型里，应满足：

```text
equity - initial_cash = realized_pnl + unrealized_pnl
```

这是一条很有价值的逐日对账恒等式，测试会检查它。

## 10. 手算一次完整交易

这一节对应 [`tests/test_accounting.py`](../tests/test_accounting.py)。
教学参数故意比默认回测成本大，方便看到影响：

```text
initial_cash = 10,000
commission_rate = 0.001   # 0.1%
slippage_rate = 0.01      # 1%
买入参考开盘价 = 100
卖出参考开盘价 = 110
```

### 10.1 买入

买入成交价：

```text
100 × 1.01 = 101
```

每股包含手续费的支出：

```text
101 × 1.001 = 101.101
```

可购买数量：

```text
floor(10,000 / 101.101) = 98 股
```

成交金额、手续费、滑点归因：

```text
trade_value = 98 × 101 = 9,898
commission = 9,898 × 0.001 = 9.898
slippage_cost = 98 × (101 - 100) = 98
```

买入后现金与成本基础：

```text
cash = 10,000 - 9,898 - 9.898 = 92.102
cost_basis = 9,907.898
quantity = 98
```

这里没有再扣 98 美元滑点。成交金额 9,898 已经比参考价金额 9,800 多了 98。

### 10.2 持仓期间估值

如果某日收盘价为 105：

```text
market_value = 98 × 105 = 10,290
equity = 92.102 + 10,290 = 10,382.102
unrealized_pnl = 10,290 - 9,907.898 = 382.102
```

此时账户盈利，但股票还没有卖出。
这里用 close 估值，不代表代码用该 close 完成买卖。

### 10.3 卖出

卖出成交价：

```text
110 × 0.99 = 108.9
```

成交金额和手续费：

```text
trade_value = 98 × 108.9 = 10,672.2
commission = 10,672.2 × 0.001 = 10.6722
slippage_cost = 98 × (110 - 108.9) = 107.8
```

最终现金与盈利：

```text
cash = 92.102 + 10,672.2 - 10.6722 = 10,753.6298
realized_pnl = 10,672.2 - 10.6722 - 9,907.898 = 753.6298
quantity = 0
equity = cash = 10,753.6298
```

总手续费为 `9.898 + 10.6722 = 20.5702`。
总滑点归因成本为 `98 + 107.8 = 205.8`。

直接运行下面代码，可以看到与手算一致的结果：

```python
from src.execution import Costs, execute_order
from src.portfolio import Portfolio

account = Portfolio(10000)
costs = Costs(commission_rate=0.001, slippage_rate=0.01)

buy = execute_order('BUY', 100, account.cash, account.quantity, costs)
account.apply_fill(buy)
print(account.cash, account.quantity)

sell = execute_order('SELL', 110, account.cash, account.quantity, costs)
account.apply_fill(sell)
print(account.cash, account.realized_pnl)
```

浮点输出末尾可能有很小的误差，所以测试使用 `pytest.approx`。
这不是允许随意改变预期金额，而是容纳二进制浮点表示误差。

## 12. backtest.py：每天到底执行哪些代码

入口 `run_backtest` 先验证数据、重置索引、计算因果指标，再分别运行策略账户和 Benchmark 账户。

`_simulate` 的逻辑可概括为以下伪代码：

```python
for i in range(len(data)):
    previous_target = target[i - 1] if i > 0 else -1

    # 开盘阶段：方向依据上一个收盘，而非今天收盘
    side = decide_side(previous_target, account.quantity)
    if side is not None:
        fill = execute_order(side, open[i], account.cash, account.quantity, costs)
        if fill is not None:
            account.apply_fill(fill)
            record_trade()

    # 收盘阶段：只估值，不用这个 close 补做今天的交易
    equity = account.cash + account.quantity * close[i]
    record_account_state()
    record_close_signal(target[i], account.quantity)
```

这里的 `decide_side` 是用于说明的伪函数，仓库直接用 if 条件实现，没有该函数。

目标与当前持仓之间的关系是：

| 前一收盘目标 | 当日开盘前持仓 | 当日开盘行为 |
| --- | --- | --- |
| `-1` | 无持仓 | 等待 |
| `1` | 无持仓 | 尝试买入 |
| `1` | 有持仓 | 持有，不加仓 |
| `0` | 无持仓 | 保持现金 |
| `0` | 有持仓 | 卖出全部 |

### 12.1 signal 列为什么看上去比成交晚一天或早一天

`equity.csv` 的一行描述当日收盘时的账户状态与新信号。
`trades.csv` 的一行描述当日开盘实际执行的交易，其 `signal_date` 来自前一行。

因此，如果 3 月 30 日 equity 行写 BUY，成交日志应在 3 月 31 日开盘出现，而不是在 3 月 30 日出现。
如果某天开盘买入成功，当天收盘目标仍为持有，则当天 signal 通常为 HOLD。
这并不表示当天没有交易，而是表示收盘时不需要再为下一日发出新的买入意图。

### 12.2 最后一日信号没有下一行可以执行

程序不会凭空生成一条额外行情来执行期末信号。
如果最后一日收盘出现 SELL，但数据已结束，当前实现仍按该收盘价估值持仓。
这也是“不强制期末清仓”的含义。

## 14. metrics.py：收益和风险该怎么看

[`src/metrics.py`](../src/metrics.py) 只读取完成后的账户曲线和成交账本，不反过来参与交易。

### 14.1 日收益与复利

```text
daily_return[t] = equity[t] / equity[t-1] - 1
```

第一行以初始资金为前值，本项目预热期没有持仓，所以这段收益为 0。
日收益的定义基于整个账户，包括现金、持仓变动和已支付成本。
它不是 SPY 的日涨跌幅。

累计收益需要连乘：

```text
累计增长倍数 = product(1 + daily_return)
```

例如涨 10% 再跌 10%，是 `1.1 × 0.9 = 0.99`，最终亏 1%，不是收支相抵。

### 14.2 Total Return：整个期间赚了多少

```text
Total Return = final_equity / initial_cash - 1
```

当前策略约为 146.67%，意思是资产从 100,000 增长到约 246,672。
这不是每年收益 146.67%。

### 14.3 CAGR：折算成每年同一增长速度

```text
years = 首末日期间隔天数 / 365.25
CAGR = (final_equity / initial_cash) ** (1 / years) - 1
```

当前策略约为 8.56%。
它描述的是首末资产之间的等效复合年增长速度，不代表每个年份都赚 8.56%。
项目使用完整日期区间，含开始阶段的现金预热，不从第一次买入才开始计时。

### 14.4 Annualized Volatility：日收益的波动大小

```text
volatility = std(daily_return, ddof=1) × sqrt(252)
```

252 是配置中的年化交易日因子，不是程序确认每个年份都有恰好 252 行数据。
波动率衡量收益离散程度，上涨和下跌的波动都会计入。

平方根年化是一种统计约定，收益有强自相关或分布变化时不能把它当成严格风险保证。

### 14.5 Sharpe：平均超额收益相对于波动

项目先把配置中的年度无风险利率折算成日利率：

```text
rf_daily = (1 + rf_annual) ** (1 / 252) - 1
excess = daily_return - rf_daily
Sharpe = mean(excess) / std(daily_return, ddof=1) × sqrt(252)
```

当前无风险利率配置为 0，Sharpe 约为 0.769。
它是一个无单位比率，不是 76.9% 收益。

注意这里用日算术均值，不是用 CAGR 直接除以波动率。
改变无风险参数只影响这些评价统计，不会让账户现金自动获得利息。

### 14.6 Sortino：只在分母中惩罚下行偏离

当前口径为：

```text
downside = sqrt(mean(min(excess, 0) ** 2))
Sortino = mean(excess) / downside × sqrt(252)
```

均值是在全部日样本上计算的，包括没有负超额收益的那些天。
它不是只挑亏损日算标准差。
不同软件可能使用不同 Sortino 定义，比较前要对齐口径。

### 14.7 Maximum Drawdown：从历史高点跌了多少

```text
peak[t] = max(initial_cash, equity[0], ..., equity[t])
drawdown[t] = equity[t] / peak[t] - 1
maximum_drawdown = min(drawdown)
```

假设净值从 100 涨到 150，再跌到 120：

```text
drawdown = 120 / 150 - 1 = -20%
```

虽然相对最初的 100 仍盈利 20%，相对曾经达到的高点却回撤了 20%。
本项目输出负数，当前策略最大回撤约为 -22.97%。

### 14.8 Calmar：增长速度相对于最大回撤

```text
Calmar = CAGR / abs(Maximum Drawdown)
```

当前约为 0.373。它依赖样本区间，也不能保证未来不会出现更深回撤。

### 14.9 成交笔数、往返次数、胜率与 Profit Factor

当前 `trade_count=45`：买入和卖出各算一笔成交。
`closed_trade_count=22`：22 次完成的买入→卖出往返。
另外有一笔买入尚未平仓，期末持有 364 股。

胜率只看已平仓往返：

```text
Win Rate = 盈利往返次数 / 全部已平仓往返次数
Profit Factor = 盈利往返的净盈利总和 / 亏损往返的净亏损绝对值总和
```

当前胜率约为 54.55%，即 22 次里有 12 次净盈利。
Profit Factor 约为 2.863。

高胜率未必意味着赚钱：如果九次各赚 1 元，一次亏 20 元，胜率 90%，总结果仍亏损。
还必须观察盈利和亏损的金额。

平均盈利、平均亏损分别在盈利与亏损的已平仓样本内计算，亏损均值输出负数。
持有期也是只对已平仓往返统计，单位为日历天。

### 14.10 Turnover：交易活动有多频繁

项目定义：

```text
Turnover = 所有买卖成交金额之和 / 平均每日账户净值
```

当前约为 44.77，表示整个回测期的累计双边成交额约为平均账户规模的 44.77 倍。
它不是年化换手率，也不是自动表示“每年 44.77 次”。

### 14.11 null 是有含义的结果

没有已平仓交易时，胜率没有定义。
没有亏损往返时，Profit Factor 的分母为零，项目返回 `null`。
没有日收益波动时，Sharpe 也没有定义。

因此 `null` 不等于 0，也不表示计算失败。
当前报告用合法 JSON 表达这些情况，不输出 NaN 或 Infinity。

## 15. Benchmark：为什么一定要有对照组

Benchmark 是用于比较的参考策略。当前使用 SPY Buy & Hold：
在第一个允许执行交易的日期买入一次，然后一直持有。
它使用同样的初始现金、整数股限制、手续费和滑点。

它不是在 2015 年第一天就买入，而是在第 61 个交易日买入，与均线策略的预热可交易时间对齐。
即使第 60 日收盘均线目标为现金，Benchmark 仍按规则在第 61 日开盘买入。

当前结果如下，数据与参数固定为本项目默认实验：

| 指标 | 20/60 策略 | SPY Buy & Hold |
| --- | ---: | ---: |
| 最终资产 | $246,671.89 | $393,896.76 |
| Total Return | 146.67% | 293.90% |
| CAGR | 8.56% | 13.28% |
| 年化波动率 | 11.57% | 17.66% |
| Sharpe | 0.7690 | 0.7959 |
| 最大回撤 | -22.97% | -33.70% |
| 总手续费 | $3,561.39 | $49.93 |
| 总滑点归因成本 | $1,424.55 | $19.97 |

这段样本里，策略收益较低，波动和最大回撤也较低。
单凭这些数字不能确定较低收益具体有多少由成本、离场时机或错过上涨造成，需要进一步做归因分析。
当前没有做这类优化或诊断实验。

收益为正并不自动说明规则有超越市场的能力。
也不能把“策略 CAGR - Benchmark CAGR”直接称为已经估计出的统计 alpha；这里没有进行风险因子回归等估计。

Benchmark 没有卖出，所以没有已平仓往返，胜率与 Profit Factor 为 null。
它仍然可以有很大的未实现盈利。这与账户逻辑完全一致。

## 16. 未来泄露：回测里最容易出现的错误

从算法工程角度，这是一类时间条件下的数据泄露。
不仅要问“这个字段来自哪一列”，还要问“在执行决策的那个时刻，这个值是否已经可得”。

常见风险：

| 操作 | 为什么可能出问题 |
| --- | --- |
| `shift(-1)` 用于策略输入 | 将下一行数据搬到当前行 |
| `rolling(..., center=True)` | 当前窗口可能包含未来行 |
| 全样本均值、标准差归一化 | 未来分布影响过去特征 |
| 用当日 high 判断当日 open 买卖 | 开盘时不知道最终日内最高价 |
| 对历史缺失特征使用后向填充 | 未来观测被填到过去 |
| 时间合并选中未来记录 | 日期标签看似对齐，但信息公布时间晚于决策时间 |

未来收益可以用来做评估标签，但必须与策略输入隔离。当前工程没有机器学习标签模块。

### 16.1 future mutation test 验证什么

[`src/validation.py`](../src/validation.py) 的检查过程：

1. 用完整数据计算指标和目标。
2. 选择一个截止日期 T。
3. 固定随机种子，猛烈修改 T 之后所有 OHLCV。
4. 重新计算。
5. 精确比较 T 及之前的指标和目标。
6. 再只传入截至 T 的数据前缀，检查与原历史前缀一致。

如果未来价格变了，昨天已经计算好的均线也变了，说明过去的计算依赖未来。
测试会抛出断言错误，不继续给出一个“看起来还能用”的结果。

变异数据故意可能违反 OHLC 关系，因此这个函数直接调用策略，不先验证或修复变异数据。
它测试的是数据依赖，不是在生成新的合法市场行情。

历史运行检查了以下截止日期：

```text
2015-03-30
2020-07-01
2025-12-30
```

除此之外，`test_no_lookahead.py` 还检查：修改未来合法行情后，过去账户曲线不变；改变明天 close 不应改变明天 open 的既定成交。

### 16.2 它不能证明什么

未来变异通过，只能说明被测计算在这些检查中没有依赖修改过的未来输入。
它不能证明供应商提供的是历史当时可见的原始版本数据，也不能证明某个策略在未来赚钱。

例如，现在下载的复权历史可能经过后来公司行动或供应商修订。
即使 rolling 实现完全因果，也不能据此把整份数据称为严格的历史时点数据。

## 17. 如何理解 tests，而不是只看绿灯

测试的价值在于验证业务事实，不是让代码调用一次没有异常。

| 测试文件 | 核心验证 |
| --- | --- |
| `test_strategy.py` | 人工均值、预热、相等时现金、非法窗口 |
| `test_execution.py` | 成交价、整数股、费用、滑点、买不起一股 |
| `test_accounting.py` | 手算往返、现金和 PnL、拒绝透支和非法卖出 |
| `test_backtest.py` | 六行完整链路、Benchmark 日期、每日对账 |
| `test_no_lookahead.py` | 日期对齐、未来变异、明日 close 不影响明日 open |
| `test_validation.py` | 非法数据拒绝、本地 Parquet、不静默修复 |
| `test_metrics.py` | 人工收益与风险指标、已平仓交易统计 |
| `test_download.py` | 模拟供应商、排他结束日期、复权设置、禁止覆盖 |

下载测试使用假的供应商对象，不联网。
人造行情使用 `pd.bdate_range`，只是构造便于检查的工作日标签，不意味着它已经复现真实交易所节假日表。

当前验证快照为 42 项通过。以后测试数量或代码变化时，应重新运行，不把这个数字当永久状态。

出现失败时，先判断是代码还是业务预期错了。
比如现金差一个滑点金额，应先检查是否重复扣除成本；成交日期差一行，应先检查是否使用了当前行 target。
不能为了得到绿灯直接把 expected 改成程序当前返回值。

## 19. 推荐的断点和排错方式

调试一笔交易时，可以按下列顺序检查：

1. 在 `strategy.py` 的 return 前看均线与 `target`。
2. 在 `_simulate` 的 `next_open_target` 后看 `i`、`bar.date` 和前一天目标。
3. 在 `execute_order` 中看成交价、费率、整数股数。
4. 在 `account.apply_fill` 前后看现金、持仓和成本基础。
5. 在收盘状态写入前看 equity、日收益和 drawdown。

这是一个事件调试过程。不要只盯最终 CAGR，因为错误可能发生在多年前的某一笔成交。

| 现象 | 优先检查 |
| --- | --- |
| 买入后现金变负 | 股数是否考虑手续费和滑点 |
| 净值少了另一笔滑点金额 | 是否重复扣除 `slippage_cost` |
| 均线已经做出正确目标，但今天过早成交 | 是否用 `target[i]` 代替 `target[i-1]` |
| 每天都有 BUY 成交 | 是否忘了检查已有持仓 |
| 卖出盈利与账户增量不一致 | 是否包括买入手续费，是否混淆累计与单次 PnL |
| Sharpe 和另一个工具不一致 | 年化因子、无风险利率、ddof、预热期口径 |
| Benchmark 胜率为 null | 当前没有已平仓往返，属于定义上的正常结果 |
| 相同代码跑出不同结果 | 数据哈希、配置、源码、依赖版本是否一致 |

## 20. 这个工程当前的能力边界

先理解已经明确采用的假设，再决定未来是否需要更精细的模型。

**开盘成交模型。** 程序假设可以按开盘价加固定滑点完成全部交易，没有模拟未成交、部分成交或订单排队。

**根据实际开盘价确定整数股数。** 程序在开盘成交步骤知道 open 后，计算最大可负担股数。
这在离线回测中是一种简化成交假设。若真实订单必须在开盘前报出固定股数，不能提前知道最终开盘价来精确用满现金。
未来若研究真实执行，需要单独定义下单时间、数量预估和价格变动约束。

**复权合成账户。** 当前账户没有显式公司行动和分红现金账本，不能视为完全还原真实历史份额与美元现金流。

**现金收益为零。** 空仓时现金不赚利息。指标中的无风险利率是评价参照，不是账户现金利息模型。

**有限的数据验证。** 程序检查行级合法性和日期顺序，但没有独立交易日历逐日核验缺失交易日。

**有限的统计证据。** 一条历史曲线、三个未来变异截止点及通过的确定性测试，支持当前基础实现的可信度；不构成未来表现或所有代码路径无误的证明。

工程规则优先于策略规范中列出的远期工作。本阶段没有参数搜索、Walk-Forward、机器学习、实盘或模拟盘。
学习时可以用很短的人造序列理解逻辑，不必先搜索“收益最好的窗口”。

## 21. 用这些问题检查自己是否真正理解

先独立回答，再看下表。

| 问题 | 答案 |
| --- | --- |
| 今天 close 很高，今天 open 能否据此买入？ | 不能，open 时还不知道最终 close |
| 今天 short_ma > long_ma，就一定出现 BUY 成交吗？ | 不一定；目标在收盘才形成，已有持仓则保持，买不起也不会成交 |
| `target=1` 为什么不意味着每天都买？ | target 是期望状态，买卖取决于它和当前持仓的差异 |
| 买完现金只剩一点，是否表示亏了几乎全部资金？ | 不是，资金主要转换成持仓市值 |
| 为什么交易日志要同时保留 raw_open 和 execution_price？ | 一个是参考价，一个是计入滑点的成交价，可复算成本 |
| 为什么不能再从现金里扣一次 slippage_cost？ | 滑点已进入成交价格与成交金额 |
| 45 笔成交为什么只有 22 次已平仓往返？ | 22 次买卖各两笔，再加一笔期末未平仓买入 |
| 期末股票上涨但没卖，净值会不会增加？ | 会，按收盘市值估值，增量属于未实现损益 |
| Total Return=146.67% 是否表示每年赚 146.67%？ | 不是，它是整个期间收益；CAGR 是复合年增长口径 |
| 策略赚钱但比 Benchmark 少，能否只凭赚钱判定策略有效？ | 不能，还需明确目标、对照表现、风险及证据范围 |
| future mutation 通过是否证明供应商历史数据没有被后来修订？ | 不能，它检查被测程序的信息依赖 |
| 回测一次为什么不自动重新下载？ | 保持数据固定，保证实验可复现 |

完成这些问题后，建议打开 `tests/test_backtest.py`，自己在纸上沿六个交易日推演一次，再对照 `_simulate`。
当每一行现金、持仓、目标和成交日期都能解释时，你就已经掌握了这套基础回测工程的核心。
